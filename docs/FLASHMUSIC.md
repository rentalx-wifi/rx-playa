# FlashMusic

Свой источник музыки для RX Playa и всё, что вокруг него. Публичный, но
живущий только внутри приложения — как бесплатные модели у OpenCode: снаружи
доступа нет, внутри всё работает без настроек.

Документ — итог интервью. Решения в нём приняты, а не предложены; открытые
вопросы вынесены отдельно в раздел 14.

---

## 1. Картина целиком

Человек ставит RX Playa, добавляет свой сервер FlashMusic в список
источников — выше JioSaavn, с возможностью выключить. Он ищет трек и видит,
что тот уже есть у него: строка с чужой платформы несёт плашку FM. Плеер
играет FLAC с сервера, а не Opus с YouTube.

Ничего общего: ни подписок, ни ленты, ни комментариев. То, что слушают
другие, приложению и серверу неизвестно — оно им и не нужно.

## 3. Архитектура

Три части, и граница между ними — `trackId`.

**Приложение.** Плеер плюс нативный `MusicSource` FlashMusic. Не аддон:
аддону доступны только `search` и `stream`, а нам нужны тиры, предзагрузка и
P2P.

**Раздача (`streamer/`).** Уже написана и измерена: FLAC → Opus, дисковый
кеш, Range. 1000 слушателей на прогретом кеше — 0.05 ядра. Отвечает за байты
и ничего не знает о людях.

**Каталог (`flashmusic/`).** Свой модуль Go: ингест, SQLite, три тира,
кеш, предкодирование, кросс-матчинг. Знает о файлах и ничего — о людях.

Части живут на prod как отдельные процессы: падение раздачи не должно ронять
каталог, и наоборот.

## 4. Модель данных

### Трек

Идентификатор не может зависеть от пути: файл переносят, перетегируют и
заменяют лучшей копией.

```
trackId = sha256(акустический отпечаток)[:16]
```

Отпечаток (Chromaprint) считается при ингесте и решает дедупликацию: один
трек во FLAC и в MP3 — один `trackId` и две рендиции.

### Рендиция

```
Rendition { codec, sampleRate, bits, bitrate, bytes, path, source }
```

`source` — откуда пришло (`upload`, `tidal`, `youtube`, …) и нужно для
правила «не выше источника» и для журнала неудач.

### Вариант исполнения

Slowed, Sped Up, Super Sped Up — это не отдельные треки, а параметр
воспроизведения. На YouTube они почти всегда получаются из обычной версии
изменением скорости, при котором тон едет вместе с ней: то есть обычным
пересэмплированием.

```
Variant { kind, rate, pitchFollowsRate, reverb, verified }
```

Хранится **один файл** и запись варианта. Приложение играет с нужным
коэффициентом — у него уже есть смена скорости без изменения тона, остаётся
добавить режим, где тон следует за скоростью.

Два ограничения, без которых это ломается:

- **Не всё выводимо.** «Slowed + reverb» часто фанатский эдит с другим
  миксом. При ингесте вариант сравнивается с растянутой копией оригинала
  (корреляция после выравнивания): совпало — `verified = true`, хранится
  только параметр; не совпало — это другой звук, хранится отдельным файлом.
- **Поиск обязан находить.** Запрос «song sped up» должен возвращать строку.
  Поэтому вариант остаётся в индексе поиска как запись, но не как файл:
  общий `trackId`, вариант — атрибут.

Выигрыш по месту прямой: шесть версий одного трека — это 150 МБ против 25.
На библиотеке в 40 тысяч, где у десятой части есть варианты, экономия —
около полутерабайта.

### Аккаунта нет

**Решение 2026-11-23:** соцсети в FlashMusic не будет, сервер остаётся
источником. Ни `User`, ни `Session`, ни привязок площадок в схеме нет и не
планируется. Подробности и что это снимает — в разделе 9.

## 5. Тиры и качество

Три тира, как решено:

| Тир | Формат | Кому |
|---|---|---|
| Lossless | FLAC, мастер как есть | по выбору, только Wi-Fi |
| High | Opus 320 | по выбору |
| Default | Opus 192 | всем, и автоматически на мобильной сети |

Правило при ингесте — **не выше источника**. Из FLAC делаем 192 и 320; из
Opus 320 делаем 192 и 320; из Opus 160 ничего не делаем выше 160.

Сервер всегда говорит правду о том, что отдал: `codec`, `sampleRate`,
`bitrate` и флаг `belowRequest`, если дал меньше запрошенного. Если мастер
когда-то был сконвертирован из 44.1 в 48, это видно, и `Lossless` на нём не
объявляется бит-в-бит копией CD.

## 6. Каталог: как пополняется

Четыре пути, по приоритету.

**1. Загрузка админом.** Основной путь для того, что есть легально. Папка
или веб-форма, дальше ингест сам всё делает.

**2. Резолв через приложение.** Сервер просит приложение найти лучшую
версию трека; приложение ищет по всем включённым источникам (модули Tidal и
Qobuz находят FLAC) и отдаёт URL. Сервер скачивает и сохраняет.

**3. Собственный поиск сервера.** Если приложение молчит, сервер ищет сам.
Порядок: сначала площадки с лосслессом, YouTube — последним.

**4. Запись потока.** Крайний случай, только для того, что иначе недоступно.

Когда лучшей версии нет, но трек популярен, остаётся копия 160 с YouTube —
помеченная как низшая рендиция.

**Журнал неудач.** Каждый трек, для которого не нашлось ничего лучше 160,
попадает в очередь на проверку: что искали, где, что нашли. Админ
периодически просматривает и ищет FLAC вручную, после чего загружает.
Журнал — это фича, а не лог: у него есть экран и кнопка «загрузить».

## 7. Кеш, офлайн, передача файлов

### Серверный кеш

Уже работает: Opus считается один раз, лежит на `/srv/flashmusic/opus`,
повторная отдача стоит ноль процессора. Топ-100 треков по прослушиваниям
не вытесняется никогда, остальное — по давности использования.

### Скачивание на устройстве

Лимит по свободному месту с порогом: приложение не забивает телефон
целиком, оставляет запас. Тир скачивания берётся из настроек, не спрашивая
каждый раз.

### Передача между устройствами

Решено: устройства передают файлы **напрямую**, сейчас — в пределах
локальной сети, через интернет — позже.

Сценарий: телефон и планшет дома. Планшет видит, что трек есть на телефоне,
и забирает его по Wi-Fi вместо повторного скачивания из интернета.

Почему локальная сеть: обнаружение через mDNS, шифрование общим ключом
аккаунта, докачка по Range — всё это укладывается в разумный объём. Пробитие
NAT между разными сетями — отдельный проект с STUN/TURN и релеем, и делать
его сразу значит не сделать ничего другого.

## 8. Очередь и предкодирование

Плеер знает очередь и говорит о ней серверу:

```
POST /api/v1/queue
{ "now": "trackId", "next": ["…", "…", "…", "…", "…"], "tier": "default" }
```

Сервер кодирует **пять треков вперёд**, всегда, как только очередь
известна. Радио и автоплей идут через ту же очередь — то есть сервер знает
будущее и на радио тоже.

Правила:

- сменилась очередь — всё старое отменяется, кодится новое;
- приоритет: играющий сейчас, затем следующие по порядку;
- если слушатель ушёл, недокодированное выбрасывается;
- повторный запрос того же трека от другого человека ничего не перекодирует
  (дедупликация уже есть).

Выигрыш не в средней нагрузке, а в худшем случае: первое прослушивание
холодного трека перестаёт быть медленным.

## 9. Аккаунты, комментарии, лента — отменено

**Решение 2026-11-23:** соцсети в FlashMusic не будет. Сервер остаётся
источником музыки: каталог, три тира, кеш, варианты исполнения. Ни
регистрации, ни профилей, ни комментариев, ни подписок, ни ленты.

Что это снимает:

- обязательный вход перед первой песней, а с ним и провал конверсии;
- почтовый сервер, SPF/DKIM/PTR и VPS, который был нужен только под него;
- модерацию пользовательского контента и риски, с ней связанные;
- хранение чужих персональных данных, а значит и выгрузку с удалением;
- обязательность аккаунта как проверку «кто слушает» — приложение и так
  знает свои устройства, а серверу это не нужно вовсе.

Что остаётся на сервере из «социального»: счётчик прослушиваний. Он не про
людей — это топ-100 для пиннинга кеша, и он обезличен.

Разделы про аккаунты, комментарии и модерацию удалены, а не отложены:
возвращаться к ним не планируется.
## 12. Эксплуатация

**Домен:** `flashmusic.space` или `rxplaya.space`, Let's Encrypt на сервере.
Выделенный IP есть.

**Раздача приложения:** GitHub Releases сейчас; позже — свой сервер
обновлений или RuStore/Google Play.

**Почта:** не нужна. Аккаунтов нет, подтверждать нечего, VPS под почтовый
сервер больше не требуется.

**Логи:** всё, 30 дней. Персональных данных в них нет: ни почты, ни токенов
площадок сервер не видит, только IP запросов и пути файлов.

## 13. Этапы

Порядок выбран так, чтобы каждый этап имел смысл сам по себе.

**Этап 1. Каталог и источник (MVP).** Ингест админских файлов, отпечатки,
таблица треков, рендиций и вариантов исполнения, три тира, нативный источник
в приложении, стриминг с сервера. Это уже рабочая музыка.

**Этап 2. Кеш и предкодирование.** Очередь, пять треков вперёд, пиннинг
топ-100, LRU.

**Этап 3. Варианты играются.** Плеер применяет `rate` из каталога; режим
«тон следует за скоростью» рядом с существующим «скорость без тона».
_Сделана половина: режим «тон следует за скоростью» есть (раздел 17), но
выбор варианта из выдачи ещё не автоматический — серверу осталось сообщить
в поиске, какой именно вариант резолвил запрос._

**Этап 4. Добыча лучших версий.** Резолв через приложение, журнал неудач с
экраном проверки.

**Этап 5. Передача файлов по локальной сети.**

**Этап 6. Listen Together на нашем каталоге.**

Полные аккаунты, комментарии и лента вычеркнуты — см. раздел 9.

## 14. Риски, которые уже созданы решениями

Здесь не советы, а следствия. Их можно принять — но не заметить нельзя.

**Бэкапов нет.** Каталог восстановим из файлов за вечер: ингест идёт со
скоростью около двухсот файлов в секунду на прогретом кеше сканов. А вот
история прослушиваний, из которой берётся топ-100 для пиннинга, живёт только
в базе на том же RAID0 из четырёх дисков 2008–2010 годов, который уже один
раз тихо испортил файл. Потерять её неприятно, но не смертельно — топ
восстановится сам за неделю-две обычного слушания.

**Публичная раздача чужого контента.** Пока сервис для себя — это личное
дело. Публичный адрес и открытая раздача чужой музыки — уже другая
категория, и жалоба приходит не в код, а на хостинг и на владельца домена.

**Обход DRM я не проектирую.** Потоки Spotify и Яндекса закрыты ключами,
которых в клиенте нет; записать их нельзя не потому, что сложно, а потому
что невозможно без взлома защиты. YouTube доступен, но это нарушение его
правил, и риск целиком на раздаче.

**Логи 30 дней.** Данные уже обезличены: сервер не знает имён, почт и
площадок, только IP и пути файлов. Всё равно нужен фильтр, который не
пропустит в лог ни токен, ни тело запроса, — иначе одна отладочная строка
станет утечкой.

**Передача файлов по сети.** Даже в локальной сети это обнаружение,
шифрование, докачка и проверка целостности. Не начинай с неё: этап 5, не
раньше.

**Всё на prod.** Раздача, сообщество, почта и бэкап на одной машине — это
одна точка отказа. Пока проект мал, это разумно; когда появится сотня
активных — раздели хотя бы сообщество.

## 15. Протокол (эскиз)

```
# каталог
GET  /api/v1/library/manifest?since=<rev>&limit=<n>
GET  /api/v1/tracks/{id}
GET  /api/v1/tracks/{id}/stream?tier=lossless|high|default
GET  /api/v1/search?q=<text>
POST /api/v1/match                 пакетная проверка чужих строк
POST /api/v1/prefetch              что слушатель собирается играть
POST /api/v1/tracks/resolve        приложение отдаёт найденный URL

# воспроизведение
POST /api/v1/tracks/{id}/play      счётчик для пиннинга

# офлайн
GET  /api/v1/peers               кто из моих устройств онлайн в сети
```

Аккаунтов, комментариев, ленты и событий в протоколе нет — раздел 9.

Манифест инкрементальный: приложение спрашивает «что изменилось после
`since`», а не перекачивает каталог. На 40 тысячах треков это разница между
8 МБ и парой килобайт при каждом запуске.

## 16. Состояние реализации

Обновлено 2026-11-23.

**Работает и проверено тестами и живым запуском:**

- `flashmusic/` — свой модуль Go, Listen Together не затронут, стример
  подключён через `replace`.
- Каталог в SQLite: `trackId = sha256(Chromaprint)[:16]`, дедупликация по
  отпечатку, кеш сканов по пути, размеру и mtime.
- Ингест: ffprobe для тегов и потоков, fpcalc для отпечатка, мастер
  выбирается по качеству и переназначается сам.
- Варианты Slow/Sped Up: скорость измеряется по отношению длительностей,
  а не берётся из названия; выводимость проверяется корреляцией формы
  сигнала после восстановления темпа. Неразрешимые остаются файлами с
  `rate = 1`.
- Три тира: `lossless` отдаёт мастер с поддержкой Range, `default` и `high` —
  Opus через дисковый кеш (повторный запрос в 76 раз быстрее).
- Предкодирование: `POST /api/v1/prefetch` заменяет план, прежняя очередь
  отменяется вместе с идущим кодированием.
- Вытеснение: LRU по mtime, топ-100 по прослушиваниям не вытесняется.
- Манифест постраничный: `?since=&limit=`, `more` в ответе; курсор — ревизия
  последнего трека страницы, поэтому листание не теряет и не повторяет ничего.
- Кросс-матчинг: `POST /api/v1/match` — один запрос на весь список выдачи,
  титул и исполнитель, возвращает только совпавшие. В приложении строка
  чужой платформы, которая есть и на своём сервере, получает плашку FM.
- Плашка источника: `HomeSource.FLASHMUSIC` с логотипом из
  `composeResources`, 15dp; в плеере — `FlashMusic Lossless` с серебряной
  версией знака вместо волн Apple Music, `FlashMusic Hi-Res` для 320 и
  `FlashMusic` для 192.
- Источники реестра участвуют в поиске «All platforms» — раньше там был
  жёстко зашитый список платформ.

Укреплено по итогам аудита кода 2026-11-23:

- Манифест: страница по умолчанию и пакетный `attach` — на библиотеке больше
  32 766 треков первая же синхронизация падала с «too many SQL variables».
  Страница, курсор и надгробия читаются в одной транзакции, поэтому трек
  больше не может приехать дважды.
- Кеш Opus: ожидающий чужого кодирования больше не получает 500, если первый
  слушатель отключился или prefetch сменил план — он ждёт по своему `ctx` и
  кодирует сам. Брошенные `.enc-*` убираются при обходе.
- Пропавший файл больше не 500: отдаётся следующая по качеству реплика с
  отдельным ключом кеша, а если нет ни одной — 404.
- Маркеры вариантов различаются: имя файла требует скобок или края названия
  («Slow Down» — песня, а не slowed-версия «Down»), поисковый запрос — нет.
- `-opus-max` делится между тирами; у rxstream появился `-opus-max` и подчистка
  по таймеру (`STREAM_OPUS_MAX`).
- Таймауты: 60 с на ffprobe/fpcalc/ffmpeg на файл, `ReadTimeout`/`IdleTimeout`
  у HTTP-сервера, `%`/`_` в поиске экранируются.

**Ещё нет:**

- Вариант Slow/Sped Up не выбирается сам: сервер знает, что запрос был про
  slowed-версию, но пока не сообщает это в ответе поиска, поэтому приложение
  играет базовый трек на обычной скорости. Механика для второй половины уже
  есть — см. «Скорость и тон» ниже.
- Первый синк большой библиотеки всё равно выкачивает каталог целиком, просто
  порциями: приложение ещё не хранит курсор и не листает манифест само.
- У сервера нет аутентификации: любой в локальной сети ищет и слушает без
  токена. У rxstream она есть — общий `token`-middleware ещё не переиспользован.

- Ингест пока только руками через `-scan`, без админского экрана.

**Отменено:** аккаунты, комментарии, лента, подписки, модерация — решение от
2026-11-23, подробности в разделе 9. Сервер остаётся источником музыки.

## 17. Скорость и тон в плеере

Сделано 2026-11-23 вместе с issue #56, потому что это две стороны одной вещи:
slowed-версия трека — это его темп с уехавшим тоном.

- `PlaybackRate(speed, pitchFollows)` в `playback/SpeedAndPitch.kt` — единственное
  место, где из скорости и намерения собираются `Media3.PlaybackParameters`:
  `pitch = 1` — коррекция включена (как было всегда), `pitch = speed` — чистое
  ресемплирование, то есть slowed/sped up.
- `PlaybackRateState` держит текущую базовую скорость (скорость слушателя плюс
  возможный вариант трека). Её читает и `CrossfadeController`, который
  умножает в неё свою битмэтч-растяжку, — иначе одна и та же скорость
  записывалась в плеер дюжиной разных мест.
- UI: шторка `SpeedSheet` (пресеты 0.5…2×, шаг 0.05, переключатель «Сохранять
  тон»), чип `0.8×` у бейджа качества (только когда скорость не 1×) и строка
  Speed в шторке вывода. Настройки → Воспроизведение дублируют пресеты и тумблер.
- Скорость глобальная: держится между треками и переживает перезапуск
  (`playback_speed`, `playback_pitch_correction`).

## 18. Хостинг и место в приложении

Сервер живёт на этой машине как пользовательский юнит systemd:

- `~/.config/systemd/user/flashmusic.service`, `-addr 0.0.0.0:8099`,
  каталог `~/Music/FlashMusic`, БД `~/.local/state/flashmusic/flashmusic.db`,
  кеш Opus `~/.cache/flashmusic/opus` с лимитом 10 ГиБ.
- `systemctl --user enable --now flashmusic` — переживает перезапуск сессии;
  журнал: `journalctl --user -u flashmusic -f`.
- Порт открыт в ufw только для домашней сети:
  `ufw allow from 192.168.10.0/24 to any port 8099 proto tcp`.
- Найденное при старте сканируется заново: `-library` включает скан, файлы
  пропускаются по кешу (размер + mtime), так что перезапуск стоит десятки
  миллисекунд.

В приложении FlashMusic занимает место JioSaavn:

- `SourceRegistry.DEFAULT_FLASHMUSIC_URL` (`http://192.168.10.140:8099`) —
  адрес, с которым источник заводится при первом запуске, уже включённым.
- JioSaavn больше не сидируется, а сохранённый в старых установках конфиг
  выбрасывается при инициализации — как это уже делалось с модулями.
- В списке источников строка FlashMusic рисует логотип (тот же, что в бейдже
  плеера) и стрелку; тап открывает отдельную страницу настроек:
  состояние (health + число треков), адрес сервера, включённость,
  кросс-матчинг и объяснение тиров.
- Кросс-матчинг выключаем (`AppSettings.flashMusicCrossMatch`) — тогда поиск
  не тратит запрос `POST /api/v1/match` на каждую выдачу.
- Приложению разрешён cleartext (`network_security_config.xml`): свой сервер —
  это HTTP в домашней сети, а не HTTPS с самоподписанным сертификатом.
